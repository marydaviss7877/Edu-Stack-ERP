Fixed Attendance can't be marked for a class's 2nd or 3rd section on the same day

backend/src/models/Attendance.ts:48 · backend/src/controllers/attendanceController.ts:31

The unique index on Attendance was { orgId, branchId, classId, date, periodNo } — it didn't include sectionId. A Class here commonly has multiple sections sharing one classId (the FA/FSC/ICS setup on every grade in this org), so markAttendance()'s upsert for a second section would collide on the sectionId-blind index and throw an uncaught E11000 duplicate key — a 500 to whoever was marking attendance.

What actually shipped (corrected — see §4)

An earlier version of this fix checked db.collection('attendance') (singular) and found no index at all, so it looked like a clean create-only fix. That check was against the wrong collection — see the §4 writeup for how that was caught. The real collection is attendances (Mongoose pluralizes "Attendance" → "attendances"), and the old buggy index was already live there, most likely built by a previously-running deployed instance of this backend against the same Atlas cluster. The actual fix: correct Attendance.ts to { orgId, branchId, classId, sectionId, date, periodNo }, drop the stale index by name from attendances, create the corrected one, and normalize away the synthetic per-stream periodNo workaround the seed data had needed.

Confirmed bug — introduced this session, caught before shipping Two seed collections were silently invisible to the real app

backend/scripts/seedMphssOrg.js · backend/scripts/seedMphssExtras.js

Both raw-driver seed scripts hardcoded MongoDB collection names, guessing Mongoose's auto-pluralization. Two guesses were wrong:

ModelGuessed (used)Actual (mongoose.pluralize())
Paperpaperspaper — singular, an irregular case in Mongoose's bundled pluralizer
Attendanceattendanceattendances

189 weekly/clearance Paper docs and 302 Attendance docs went into collections the real Paper/Attendance Mongoose models never query — invisible to the actual app, including the just-fixed unique index (built against the wrong attendance collection, so the real bug on attendances was untouched). Caught because the user explicitly asked for API-level verification instead of a browser check — a request to grade a "scheduled" clearance exam 404'd with "Clearance paper not found" even though the linked paper clearly existed in the DB. Tracing that down to a Mongoose-vs-raw-driver collection name mismatch is exactly the kind of thing a browser click-through wouldn't have surfaced as clearly as a direct API assertion did.

Fix

Migrated all documents from the wrong collections into the correct ones (same _ids, so every foreign-key reference — ClearanceExam.clearancePaperId, PaperResult.paperId — kept working), rebuilt the schema's indexes on the correct collections, dropped the wrongly-named ones, and fixed both seed scripts + fixAttendanceIndex.js so a future re-run won't reproduce this. One-time migration script: backend/scripts/fixCollectionNames.js.

Confirmed bug — pre-existing, unrelated to this session's other work branch_principal could never actually save Branch Settings

backend/src/middleware/rbac/permissions.ts (branch_management) · backend/src/controllers/branchController.ts (updateBranch)

SettingsPage.tsx — the branch-level settings page, rendered for branch_principal/accountant/it_admin — has always saved via PUT /api/branches/:id. But permissions.ts only granted branch_principal the read action on branch_management, never update (and it_admin's configure action doesn't match any action the route actually checks for). So clicking "Save Settings" on that page has always 403'd for its own intended users — not something this session's new thresholds card broke, just something it was the first thing to actually get verified against.

Fix

Added update to branch_principal's branch_management actions. That alone exposed a second, adjacent gap:

Follow-on gap, fixed in the same pass updateBranch had no per-branch ownership check

backend/src/controllers/branchController.ts

updateBranch's query was always { _id: req.params.id, orgId } — scoped to the org, never to the caller's own branch. Harmless while only group_admin/super_admin (legitimately org-wide) could reach it; the moment branch_principal got update above, a principal of one branch could edit any branch in the org by ID. Caught immediately by verifying the fix, not by inspection — the first real test of "update as branch_principal" landed on a different branch than the logged-in principal's own.

Fix

Added an explicit check: if role === 'branch_principal' and req.params.id !== branchId, 403. group_admin/super_admin remain unrestricted across the org.

Applies to mobile — already covered by the backend fix Attendance index bug

mobile/lib/screens/teacher/attendance/mark_attendance_screen.dart · mobile/lib/services/attendance_service.dart

Mobile's MarkAttendanceScreen has a real "Period" dropdown (1–8) and AttendanceService.submitAttendance() requires an explicit periodNo — unlike the web app, which never sends one. That's actually a more direct trigger for the same bug: two teachers marking attendance for different sections (FA, ICS) during the same numbered period on the same day — an everyday occurrence, not an edge case — hit the identical sectionId-blind unique index. Since the fix was at the schema/database level, it protects every client automatically; verified by replaying mobile's exact request shape (explicit shared periodNo, not omitted) against the fixed index:

FA, Period 1: 200 true
ICS, SAME Period 1, same day (mobile's real pattern): 200 true

No mobile-side code change needed or made.
